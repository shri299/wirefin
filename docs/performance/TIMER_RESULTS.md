# Timer scan evidence

Measured 2026-08-19 on the same ARM64 macOS host (Darwin 25.5.0), OpenJDK
21.0.12, JMH 1.37, one benchmark thread, `-Xms1g -Xmx1g`. Each score is the
average time to scan all named synthetic active connections whose SYN timer is
not due. The synthetic receive capacity is one byte so the experiment isolates
timer polling rather than reserving 6.5 GiB at 100k connections.

Baseline is untouched `main` at `a56e3dc`; candidate is the working tree based
on `142dcf4`. Raw JSON was generated by `scripts/benchmark-timers.sh` and is not
committed because it contains local paths. Reproduce on the target Linux host
before treating these numbers as capacity guidance.

| Connections | Baseline scan | Candidate scan | Baseline allocation/scan | Candidate allocation/scan |
|---:|---:|---:|---:|---:|
| 1,000 | 0.081 ms | 0.013 ms | 480,001 B | 0.087 B |
| 10,000 | 1.021 ms | 0.334 ms | 5,440,007 B | 2.280 B |
| 100,000 | 14.950 ms | 6.107 ms | 54,400,102 B | 41.689 B |

The baseline queried bytes-in-flight twice before determining that no timer was
due. Reordering the persist guards and calculating flight size only after a due
timer removes that allocation from the common not-due path. All 82 tests pass
after the change.

The scan is still linear. At 100k synthetic entries it consumed roughly 6.1 ms
per poll on this host, but Wirefin's current table limit is 65,536 and default
per-connection buffers make this synthetic population unlike a real deployment.
A timing wheel would add expiry migration, cancellation, wraparound, and
concurrency complexity. It is therefore not implemented yet; Linux workload
profiles should establish timer polling as a material cost first.
